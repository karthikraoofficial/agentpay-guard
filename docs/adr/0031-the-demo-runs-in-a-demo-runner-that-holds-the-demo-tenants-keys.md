# The demo runs in a Demo runner that holds the Demo Tenant's keys

The web app's /demo page lets a visitor play a Scenario: ShopBot asks for a Decision, pays, Asha approves a step_up, a reviewer signs off an Evidence pack (#272). Every call is a real call against the hosted API, so something has to hold the Demo Tenant's keys. We put them in a **Demo runner** (#273): a small server process, `python -m demo_runner`, that runs beside the API on the hosted VM, behind Caddy at `https://<AGENTPAY_API_HOST>/demo-runner/`. The browser asks it to start a run for a Scenario and then for each next step. The runner makes the API calls with the Demo Tenant's keys and answers each step with a card: the chat lines, the tool or route, the request and response, and the Decision's fields. The browser never holds a key.

We considered two other shapes. **Next.js server routes on Vercel** could hold the keys and call the API. But the keys would then be secrets on Vercel as well as on the VM, and the step engine would need a TypeScript copy beside the Python one that `python -m demo` and CI already run, which could drift from it. **Short-lived visitor keys**, minted per visit and handed to the browser, would give every visitor a key holding both `decide` and `consent` (or two keys in one page). That is the one combination ADR-0011 exists to prevent: a single client that can both ask for a payment and approve it. A Demo runner keeps one step engine in one language, keeps the keys on the VM, and gives the Agent's calls and the Payer's approval separate homes. Agent steps go through the runner with the decide key. Asha approves on the real consent screen through a Consent link.

What may surprise a reader is that the Demo Tenant is now named in config. Until now it was an ordinary Tenant that no code treated differently. Its keys are still ordinary keys, and the API still treats it like any other Tenant. But the runner's settings name them (`AGENTPAY_DEMO_AGENT_KEY`, `AGENTPAY_DEMO_TENANT_KEY`), and refuse anything but test keys (`apg_test_...`), because a public page must never sit in front of a live key.

The hosted demo runs with `AGENTPAY_ENV=production`, where `api.admin` issues live keys by default, so its Demo Tenant's keys are issued with `--test` (`create-tenant Demo --test`, or `create-key --tenant <id> --scopes ... --test`). The prefix says only what a key is for. The API treats test and live keys the same, so the Demo Tenant stays an ordinary Tenant. _(Added: #291, after the first hosted deploy found the Demo Tenant's keys were live.)_

## Consequences

- **The runner is an HTTP client of the API, like the MCP server (ADR-0029).** `demo_runner/` and the step engine in `demo/` import nothing from `core.policy`, `api`, `adapters`, `workflows`, `agents`, `evals` or `anthropic`, and `core/` imports neither. An architecture test checks this. Agent steps call `guard_mcp`'s tool layer (`guard_mcp.server.call`) with the decide key, so a demo Decision is made exactly as an Agent in an MCP host would make it.
- **One step engine.** `demo/engine.py` plays a Scenario one step at a time for the runner, for `python -m demo --scenario <id>`, and for the parametrised test that runs every Scenario file against the in-process app.
- **Its settings are separate from the API's.** `DemoRunnerSettings` holds the two keys, the API's base URL, `AGENTPAY_WEB_ORIGIN` (the only CORS origin), the rate limits and the run TTL, and none of the database, rail or model settings. On a bad setting, the runner exits 1 naming the setting, never echoing its value.
- **No model call of its own.** An Intent check is `POST /v1/intents` under the Demo Tenant, so the Model spend cap (ADR-0020) bounds every model call a visitor can cause.
- **Rate limits.** Runs started per client IP per minute, and runs in progress overall, are both in settings. Past either, the runner answers 429 with `Retry-After`. Caddy's `X-Forwarded-For` gives the client IP (uvicorn runs with proxy headers on).
- **Each run grants its own Payer, Agent and Mandate,** so concurrent visitors never share Spent this month, Velocity or New merchant history. The Demo Tenant's data grows with every run. That is fine for a demo that resets with its database, and its Audit chain stays a true record of what visitors did.
- **Idempotency.** Each step that writes has its own idempotency key. A step retried after a lost answer reuses it, and asking again for the step just run returns its card, so a double click never makes two Decisions or two Payments.
- **Run state lives in the runner process** with a TTL. One runner on one VM is enough (ADR-0021). A restart ends the runs in progress, and keeping runs across restarts is out of scope.
- **Deployment.** It is its own service in `infra/docker-compose.prod.yml`, from the same image, and `infra/smoke-prod.sh` checks its `/healthz` through Caddy. The provision wizard's Demo Tenant stage writes both keys to the VM's `.env` and starts it. Until then it restarts without serving.
